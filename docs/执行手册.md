这份手册给项目实际执行者使用。执行目标不是堆功能，而是先交付一个能扫码进入、能稳定演示、能替换人物资料、能在服务失败时继续工作的数字纪念 H5 模板。

## 一、总原则

1. **先垂直闭环，再扩展能力。** 每个阶段都必须能独立演示和回退。
2. **人物资料、页面体验、服务商 API 分层。** 页面不保存密钥，也不直接依赖某一家模型或语音服务。
3. **演示模式始终可用。** 网络、模型或语音服务失败时，用户仍能看到明确、经过审核的回答。
4. **不确定的生平信息不猜。** 人物边界优先于“回答得像”。
5. **所有页面明确标识 AI 生成。** 不暗示真人意识、实时在线或真实意志。
6. **小步提交。** 每次改动只解决一个可验收问题，保留可回退状态。

## 二、项目应保持的四层结构

### 1. 人物包层：`profiles/`

负责保存可替换的人物资料，不放页面逻辑。每个人物至少包含：

- `id`、姓名、简介、素材来源
- 语气、习惯、已审核事实
- 明确的回答边界
- 语音模式和语音资源标识
- 授权/素材处理记录（真实人物启用前必须补齐）

新增人物应当只需要新增或替换配置文件，不修改页面代码。

### 2. 体验层：`web/`

负责手机页面、对话状态、人物配置加载、演示问答、语音播放和错误提示。

- 页面不暴露任何服务商密钥。
- 通过人物 `id` 加载配置。
- 真实服务不可用时回退到演示回答。
- 语音播放失败时要恢复按钮状态，并提供文字回答或预置音频替代。

### 3. 服务适配层：`server/`

负责把前端请求转给大模型、TTS 和可选 ASR 服务。

- 先定义稳定的内部接口，再接具体供应商。
- 密钥只放服务端环境变量。
- 设置超时、有限重试和清晰错误码。
- API 失败必须返回可识别的降级信号，不能让页面无限等待。

### 4. 交付层：`scripts/` 与 `docs/`

负责启动、打包、生成二维码、素材检查、演示脚本和验收清单。交付流程不能依赖执行者临时记忆。

## 三、当前阶段的执行顺序

### P0：先把本地 Demo 做成可复制的 MVP

- 补充 HTTP 启动方式，避免要求用户直接双击页面。
- 让 `web/app.js` 读取 `profiles/demo.json`，读取失败时才使用内置默认资料。
- 支持通过 URL 参数选择人物，例如 `?profile=lin-shu-demo`，并限制可加载路径。
- 保留欢迎语、建议问题、回答、重置和 AI 免责声明。
- 完成问答等待、空输入、重复提交、网络失败和语音失败状态。
- 用手机尺寸完成一次浏览器冒烟验收。

**P0 闸门：** 新环境能按说明启动；换一个人物 JSON 后页面能显示新资料；问答、语音和演示回退都能工作。

### P1：建立真实服务的边界

- 写出 `/api/profile`、`/api/chat`、`/api/tts` 的最小接口契约。
- 增加服务端适配层和环境变量示例。
- 真实 API 超时或失败时，页面自动回到审核过的演示回答。
- 明确回答来源状态：演示回答、真实模型回答、服务失败。

**P1 闸门：** 前端无需改代码即可切换演示/真实模式；密钥不出现在浏览器；服务失败不会阻断核心体验。

### P2：补齐交付和虚构人物试点能力

- 一键启动和一键打包。
- 根据人物 `id` 生成专属链接和二维码。
- 补齐产品说明、5 分钟演示脚本、MVP 验收清单、素材采集清单。
- 用 1 个虚构人物完成内部试点。
- 记录进入成功率、首答延迟、失败率、素材处理时间和失真问题。

### P3：已授权真实人物试点和真实服务

- 在项目负责人提供已完成授权的真实人物包后，执行 1 个真实人物内部试点。
- 记录真实素材处理耗时、回答失真问题和家属反馈。
- 选择真实模型、TTS 和可选 ASR 服务并完成现场复验。
- 动态形象作为独立验收目标，不与真实人物试点绑定。

## 四、完成标准

一个功能只有同时满足以下条件，才算完成：

- 在手机尺寸下可操作。
- 有明确的成功、等待、失败和重试状态。
- 不依赖执行者本地的隐含配置。
- 失败时仍有可用回退路径。
- 文档说明了启动方式和验收步骤。
- 不引入超出当前阶段的后台、直播、训练或多服务商复杂度。

## 五、执行中的检查重点

每次提交前检查：

1. 人物资料是否来自配置，而不是散落在页面代码里。
2. 新增回答是否有资料依据，是否触碰人物边界。
3. 前端是否出现密钥、供应商私有参数或未经审核的原始资料。
4. API 失败、浏览器不支持语音、刷新页面和重复点击是否可控。
5. 是否增加了暂不做的功能，或让回退路径变得不可用。

## 六、汇报格式

执行者每次汇报只需回答四件事：

- **已完成：** 对应哪个任务和文件。
- **已验证：** 用什么环境、什么步骤验证，结果是什么。
- **风险/阻塞：** 哪些问题会影响下一阶段。
- **下一步：** 下一个可验收的小目标。

不要只汇报“代码写完了”；必须附上可复现的启动命令、测试步骤或页面截图/录屏说明。
